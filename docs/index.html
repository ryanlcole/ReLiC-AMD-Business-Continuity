1 · ReLiC definition

ReLiC = Remember · Exist · Live · Imagine · Create

ReLiC Share adds Share as the hackathon inspection/proof surface.

REMEMBER → EXIST → LIVE → IMAGINE → CREATE → SHARE → REMEMBER

EI = Environmental Intelligence. ReLiC is defined by project canon as Environmental Intelligence and continuity infrastructure.

REMEMBER

Retain errors, corrections, governing records, successful states, provenance, decisions, and reasons for change.

EXIST

Resolve relevant authority, provenance, time, errors, and context before dependent action.

LIVE

Represent current environment from interfaces actually connected and authorized.

IMAGINE

Produce traceable context/report packages retaining source, time, authority, uncertainty, tests, and results.

2 · Engineering problem

A system can possess records that were true, applicable, corrected, superseded, successful, failed, or proposed at different times. Flattening them into undifferentiated context can destroy why a decision occurred and can allow stale information to masquerade as current state.

SOURCE → IDENTITY → TIME → PROVENANCE → RELATIONSHIPS → APPLICABILITY → DECISION → EVIDENCE → RESULT → REMEMBER

ReLiC Share therefore keeps representation separate from truth; historical state separate from current state; and proposal, execution, and verified result distinguishable.

4 · RuneCore

RuneCore is the structured-meaning layer. An AuthorityRune is a bounded representation of a sourced authority-bearing record. Current fields preserve ID, record type, title, source, issuer, scope, effective date, and status.

AuthorityRune
 ├─ id
 ├─ record_type
 ├─ title
 ├─ source
 ├─ issuer
 ├─ scope
 ├─ effective_date
 └─ status

RuneCore loads authority records, change history, known-working references, and neurons. Its continuity_snapshot() inventories these records. It does not establish that a represented source is valid law, factually true, or applicable merely because a Rune exists.

Engineering purpose: preserve record identity and provenance so downstream AI or software does not have to treat an unsourced explanation string as the authority itself.

5 · Human-law boundary and source architecture

ReLiC canon establishes a hard boundary: internal AI/project authority cannot authorize violation of applicable human law. The hackathon repository contains a researched architecture describing how legal source records should enter ReLiC without pretending that ReLiC has already ingested or adjudicated all human law.

Why “all human law” cannot be one static file

Law is distributed across jurisdictions and authority classes and changes over time. Statutes, regulations, judicial decisions, constitutions, treaties, administrative material, state law, and local ordinances are not interchangeable. Source discovery also does not by itself establish applicability or precedence.

Source families currently registered

Federal legislation

Congress.gov, U.S. Code/OLRC, GovInfo Statutes at Large.

Federal regulation

Federal Register, eCFR, GovInfo CFR.

Federal judiciary

Supreme Court opinions and federal court materials.

North Carolina

General Statutes, Session Laws, Administrative Code/Register, appellate opinions and court rules.

Local government

County and municipal ordinance sources must be resolved dynamically for the jurisdiction involved.

Treaties / international agreements

Separate authority family; applicability must be established rather than assumed.

Required ReLiC legal-record path

EVENT / QUESTION
   ↓
JURISDICTION + SUBJECT + RELEVANT TIME
   ↓
CANDIDATE AUTHORITY FAMILIES
   ↓
AUTHORITATIVE SOURCE + SOURCE IDENTITY
   ↓
VALID TIME + RECORDED TIME
   ↓
AMENDS / CORRECTS / REPEALS / SUPERSEDES / INTERPRETS
   ↓
APPLICABILITY + PRECEDENCE ANALYSIS
   ↓
SUPPORTED RESULT ──or── UNKNOWN / HUMAN REVIEW
   ↓
TRACEABLE REPORT → REMEMBER

Critical rule: ReLiC must not implement shortcuts such as “newest wins” or “federal always beats state.” If jurisdiction, applicability, validity, or precedence cannot be established from evidence, the result remains unknown or requires human review.

6 · Optional Model Context Protocol adapter

MCP is not required for ReLiC to function. The repository contains app/mcp_server.py as an optional read-only interoperability experiment. Its purpose is to make selected ReLiC Share resources and deterministic inspection functions available to a compatible MCP host without redesigning ReLiC around that protocol.

Why it may be useful

If the hackathon environment or a later external agent/AI host supports MCP, the adapter provides a standard way to request ReLiC context. If no relevant host requires MCP, the adapter can remain unused. ReLiC's core architecture is unchanged either way.

Current optional surface

resources:
  relic://canon
  relic://errors
  relic://authority
  relic://human-law/sources
  relic://human-law/architecture
  relic://changes
  relic://working-references
  relic://neurons
  relic://demo/policies

tools:
  get_continuity_snapshot()
  evaluate_demo_refund(...)
  get_human_law_source_registry()

Boundary

The adapter is intended to be read-only. It does not define ReLiC canon, determine truth, establish legal applicability, mutate authority, execute AMD workloads, or become a required internal dependency.

Current verification state: source exists in the repository. A running/deployed MCP service and host interoperability have not been established here, so the report does not call them verified.
