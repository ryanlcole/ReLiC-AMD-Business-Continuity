1. Abstract

ReLiC Share is the hackathon proof surface for ReLiC. Project canon defines ReLiC as Environmental Intelligence and continuity infrastructure. The engineering concern addressed here is not merely storing information: it is preserving the identity, provenance, time, authority, correction history, reason for change, and verification state of information so that later AI or software does not silently substitute a new representation for the governed state.

The current prototype demonstrates a deterministic business-policy resolver, temporal continuity, typed authority representation through RuneCore, durable error/change/reference records, a researched human-law source architecture, a FastAPI surface, an AMD/vLLM connection boundary, tests, and an optional MCP adapter. Features not verified are identified as such.

2. Problem statement

AI-assisted development can change context every time a new answer or artifact is generated. A newer answer can be shorter, differently organized, or based on a narrower context window and accidentally omit material that was previously correct. If the newest representation is treated as truth, continuity is lost.

The same problem exists in operational records: policies are amended, corrections arrive later, environmental state changes, rules expire, and historical settings can remain useful evidence without remaining current authority.

Failure pattern:
old accurate context + new context → regenerated representation → omitted/changed prior meaning

Required pattern:
prior governed state + new evidence → compare → justify proposed change → verify → approve → preserve trace → publish

3. Project objectives

Continuity

Preserve what was known, why it was accepted, when it applied, and what later changed.

Truth discipline

Keep repository fact, project canon, recorded history, verified result, proposal, and unknown distinguishable.

Governed change

Prevent AI-generated revisions from silently replacing governed information merely because a new response exists.

Proof

Let a reviewer drill from report statements into public source, evidence, errors, and implementation.

Environmental awareness

Represent current environment only from interfaces actually connected and authorized.

Integration boundary

Keep reference/context authority separate from execution authority.

4. Engineering requirements

R1 — Preserve identity. Similar output must not collapse distinct records into one identity.
R2 — Preserve provenance. Important claims retain their source or evidence relationship.
R3 — Preserve time. Historical validity and the time a fact was learned can be different.
R4 — Preserve corrections. Superseded information remains historical evidence rather than being silently erased.
R5 — Preserve why. Material changes retain their reason and authority, not only their final result.
R6 — Unknown remains unknown. Missing evidence cannot be converted into fact by confidence.
R7 — Separate observation from execution. Seeing state does not itself authorize mutation.
R8 — Human law remains a boundary. Internal project authority does not authorize violation of applicable law.
R9 — Report continuity. A report revision must not silently omit governed content simply because it was regenerated.

5. ReLiC lifecycle and terminology

ReLiC = Remember · Exist · Live · Imagine · Create. ReLiC Share adds Share as the hackathon inspection surface.

REMEMBER → EXIST → LIVE → IMAGINE → CREATE → SHARE → REMEMBER
REMEMBER

Errors, corrections, canon, applicable authority, known-working states, provenance, decisions, and reasons for change.

EXIST

Continual reference boundary: resolve authority, provenance, time, errors, and current context before dependent action.

LIVE

Observe the current environment through available authorized interfaces while keeping historical observations historical.

IMAGINE

Permit hypotheses and simulations while keeping them distinct from evidence, tests, and results.

CREATE

Construct traceable context/report packages retaining source, authority, uncertainty, tests, and result.

SHARE

Expose the hackathon implementation and its proof for review. Share is a window into ReLiC, not a replacement for ReLiC.

7. Preservation-first change control

This project now identifies the report-regeneration problem directly: new context must not silently replace existing governed information. For material AI-proposed changes, preservation is the default until the proposed change can establish that it is necessary, accurate, and approved.

1 · NECESSARY

Identify the defect, contradiction, new requirement, superseding authority, or verified environmental change requiring modification. A different model preference is not enough.

2 · ACCURATE

Provide provenance/evidence supporting the proposed state. Unknown remains unknown; plausibility is not verification.

3 · APPROVED

Identify the human or authority empowered to approve the affected scope. An AI proposal does not automatically approve itself.

PRIOR GOVERNED STATE
       ↓
PROPOSED CHANGE
       ↓
NECESSITY EVIDENCE
       ↓
ACCURACY EVIDENCE
       ↓
APPROVAL
       ↓
MUTATION
       ↓
VERIFICATION
       ↓
RESULTING STATE + RETAINED HISTORY

Omission matters. Removing an explanation, source, limitation, proof item, or relationship from an authoritative report can change its meaning. Therefore omission is treated as a material change when it alters governed content.

This page states the owner-approved design requirement. The repository's existing canon already requires material changes to retain prior state, evidence/trigger, authority, reason, verification, and resulting state; further enforcement code remains future implementation.

8. RuneCore

RuneCore is ReLiC Share's structured-meaning layer. A Rune is a bounded representation of a sourced record. The current AuthorityRune retains record identity and metadata instead of reducing authority to an unsourced sentence.

AuthorityRune
├─ id
├─ record_type
├─ title
├─ source
├─ issuer
├─ scope
├─ effective_date
└─ status

RuneCore currently loads authority, change history, known-working references, and neurons. Its continuity snapshot inventories these records and identifies whether the human-law boundary record is present.

What RuneCore does not do: the existence of a Rune does not prove that the represented statement is true, that a legal source applies, or that execution is authorized. RuneCore structures meaning and provenance; it does not manufacture authority.

9. Temporal continuity

The temporal module separates valid time from recorded time. Valid time describes when a record applies. Recorded time describes when the system learned or recorded it. This permits a later correction to affect interpretation of earlier events without pretending the correction was known earlier.

record identity
├─ valid_from / valid_to   → when it applies
├─ recorded_at             → when it became known here
├─ source
├─ authority_id
└─ supersedes              → relationship to prior record

The implementation can reconcile historical work against later-known authority while preserving the original work record. A calculated delta remains a calculation; actual payment/recovery remains subject to applicable authority and review.

10. Human-law boundary

ReLiC's project authority remains subordinate to applicable human law. The repository contains a source architecture rather than claiming that every law has been ingested or that software can autonomously determine every legal question.

Federal legislation

Congress.gov, U.S. Code/OLRC, GovInfo Statutes at Large.

Federal regulation

Federal Register, eCFR, GovInfo CFR.

Judiciary

Supreme Court and appropriate federal/state court materials.

North Carolina

General Statutes, Session Laws, Administrative Code/Register, appellate decisions and court rules.

Local

County and municipal sources resolved for the relevant jurisdiction.

Treaties/international agreements

Separate source family whose applicability must be established rather than assumed.

QUESTION → JURISDICTION + SUBJECT + TIME → AUTHORITATIVE SOURCE
→ VALIDITY / AMENDMENT / SUPERSESSION → APPLICABILITY / PRECEDENCE
→ SUPPORTED RESULT or UNKNOWN / HUMAN REVIEW → TRACE

Shortcuts such as “newest wins” or “federal always beats state” are not sufficient legal resolution rules.

12. MCP interoperability experiment

The repository contains a read-only Model Context Protocol adapter. MCP is not required for ReLiC. It is an optional edge interface that may be useful when an external compatible host needs standardized access to selected ReLiC resources or deterministic inspection tools.

Its intended boundary is read-only: it does not define canon, determine truth, establish legal applicability, mutate authority, or execute AMD workloads. A running/deployed MCP service and host interoperability are not currently claimed as verified.

15. Limitations and non-claims

This project does not currently claim: a complete corpus of human law; universal legal applicability or precedence resolution; legal advice; deployed MCP interoperability; verified AMD-backed inference on the latest integration; AMD hardware-health telemetry or tuning; silicon-level error prevention; Evolus integration; autonomous enforcement of the new three-gate change-control requirement; or production deployment.

These limitations are part of the engineering report rather than omissions. A future revision should move an item out of this section only when evidence justifies that change.

16. Future work

The highest-value next engineering step is to turn preservation-first change control from a documented requirement into executable enforcement: compare a proposed report/state against its governed predecessor, classify every material difference, require evidence for necessity and accuracy, require appropriate approval, run verification, and only then promote the new state. That directly addresses the context-loss failure observed while building this report.

After that, event-specific AMD interfaces can be connected and verified without weakening the continuity model. Optional MCP interoperability should be tested only if the event environment benefits from it.

17. Engineering doctrine

Corrections remain evidence.
