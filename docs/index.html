1 · Definition and terminology

ReLiC = Remember · Exist · Live · Imagine · Create

ReLiC Share adds Share as the hackathon inspection and proof surface.

REMEMBER → EXIST → LIVE → IMAGINE → CREATE → SHARE → REMEMBER

EI means Environmental Intelligence. In this repository, ReLiC is defined by project canon as Environmental Intelligence and continuity infrastructure. Share is not a replacement for ReLiC; it is the public surface through which the hackathon implementation, evidence, errors, status, and source can be inspected.

Produce traceable context or reports that retain source, time, provenance, authority, uncertainty, errors, tests, and results.

2 · Engineering problem addressed by this prototype

The prototype addresses a continuity problem: a system can possess multiple records that were true, applicable, successful, corrected, superseded, or merely proposed at different times. Flattening those records into a single undifferentiated context can lose why a decision was made and can allow old information to be treated as though it were current.

The hackathon demonstration therefore separates record identity, effective time, recorded time, correction/supersession, evidence, decision output, and verification status. It does not claim that storing a record makes the record authoritative or that a model explanation makes a conclusion true.

SOURCE RECORD
     ↓
IDENTITY + TYPE + TIME + PROVENANCE
     ↓
CORRECTION / SUPERSESSION / APPLICABILITY
     ↓
CURRENT DECISION CONTEXT
     ↓
DETERMINISTIC RESULT + EVIDENCE IDS
     ↓
TRACE / REPORT
     ↓
NEW EVIDENCE RETURNS TO REMEMBER

Truth contract

REPOSITORY FACT — directly inspectable in this repository.
PROJECT CANON — a governing project rule, not automatic proof of an external-world claim.
VERIFIED RESULT — a result with identified verification evidence.
LEDGER RECORD — a durable project record of an event or correction; not automatic verification of the current commit.
PROPOSAL / HYPOTHESIS — not established as fact.
UNKNOWN — evidence is insufficient; no missing fact is invented.

4 · RuneCore — what it is and why it exists

RuneCore is the prototype's structured-meaning layer. In the current hackathon code, it converts authority-bearing project records into typed AuthorityRune objects and loads the other continuity ledgers needed to describe the state of ReLiC Share.

A Rune in this implementation is a bounded representation of a sourced record. The current AuthorityRune preserves the record's ID, type, title, source, issuer, scope, effective date, and status. That means downstream code can refer to the identity and metadata of the record without reducing it to an unsourced sentence.

RuneCore deliberately does not decide that a record is legally valid, factually true, or applicable merely because it can represent it. The source code states this boundary directly. This implements the project doctrine that structured representation does not manufacture authority.

AuthorityType = Literal[
  "human_law", "canon", "rule", "memorandum", "decision",
  "correction", "error", "working_reference", "plan"
]

@dataclass(frozen=True)
class AuthorityRune:
    id: str
    record_type: AuthorityType
    title: str
    source: str
    issuer: str
    scope: str
    effective_date: str
    status: str

What RuneCore loads today

Authority

data/relic/authority.json supplies machine-readable authority records.

Change history

data/relic/change_history.json preserves material project changes and their recorded reasons/status.

Working references

data/relic/working_references.json preserves a known-working recovery/comparison reference.

Neurons

data/relic/neurons.json organizes active plans, dependencies, goals, status, and next work. Canon states that neurons organize; they do not legislate.

What continuity_snapshot() does

It inventories the authority IDs and authority types currently loaded, counts change records, working references, and neurons, and reports whether a human_law boundary record is present. It is an inventory function—not an authority adjudicator.

return {
  "authority_ids": [rune.id for rune in authorities],
  "authority_types": sorted({rune.record_type for rune in authorities}),
  "changes": len(load_change_history()),
  "working_references": len(load_working_references()),
  "neurons": len(load_neurons()),
  "human_law_boundary_present": any(
      rune.record_type == "human_law" for rune in authorities),
}

Engineering purpose: RuneCore gives ReLiC Share a stable way to preserve identity and provenance around the records used for continuity. It prevents the implementation from having to treat an explanation string as though that string were the underlying authority record.

5 · Temporal continuity — why two clocks are retained

The temporal module distinguishes valid time from recorded time. valid_from/valid_to describe when a rate record applies; recorded_at describes when ReLiC Share learned or recorded that fact. These clocks can differ.

This distinction matters when a correction is learned after the work to which it applies. The prototype can ask what was known at an earlier time using known_at, determine which records have been superseded, and calculate a reconciliation against the authority now known to apply without rewriting the original work/payment record.

RatePeriod
 ├─ id
 ├─ person_id
 ├─ amount
 ├─ valid_from / valid_to     ← when it applies
 ├─ recorded_at               ← when it was learned
 ├─ source
 ├─ authority_id
 └─ supersedes                ← relationship to prior record

WorkRecord remains unchanged
        │
        ▼
reconcile_history(...)
        │
        ▼
Adjustment = calculated difference + authority_id

The code explicitly limits the meaning of that calculation: a positive or negative delta is mathematical output. Actual payment or recovery remains subject to applicable law, contract, authority, and review.

8 · Neurons — what the term means here

A Neuron in this hackathon repository is a machine-readable planning/dependency record. Each neuron can identify its kind, title, status, dependencies, goal, and next work. Neurons organize project intent and dependency relationships; they do not create authority and they do not override canon.

For example, NEURON-AMD is currently recorded as blocked_until_verified_amd_interfaces. Its goal is verified AMD-backed inference and, where authorized interfaces exist, testing Environmental Intelligence against current processor/system telemetry. Its recorded next steps are to configure the event endpoint, verify AMD execution, identify authorized telemetry interfaces, and record verification evidence.

9 · AMD integration boundary

The repository has connection code for an event AMD-hosted OpenAI-compatible vLLM endpoint, but the repository does not currently establish that an AMD endpoint has been configured and verified. The distinction is deliberate:

CONNECTOR CODE EXISTS                 = repository fact
ENVIRONMENT VARIABLES ARE PROVIDED   = configuration state
REQUEST SUCCEEDS                      = runtime result
ENDPOINT IS VERIFIED AMD-BACKED       = separate infrastructure evidence
AMD TELEMETRY/TUNING IS CONNECTED     = separate integration evidence

Therefore ReLiC Share does not claim AMD-backed inference execution, AMD hardware-health telemetry, processor tuning results, or silicon-level error prevention at this stage.
